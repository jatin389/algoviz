What the codebase actually said

Five facts, each with a consequence

  1. Every existing domain drives exactly one generator through useStepPlayer.

    useGraphTraversal.ts and usePathfinder.ts each call createGenerator once, returning one algorithm generator. No domain interleaves multiple sequences today.

    Consequence: the interleaving has to resolve to one linear tape before playback — the player itself can't juggle several sequences at once.

  2. The seeded RNG already has a "choose one of N" primitive — just never used.

    Rng.pick<T>() exists in src/utils/rng.ts's public API; grepping the whole codebase, it's called only from its own test file.

    Consequence: using it for real sampling is a first production use of an existing API, not new plumbing.

  3. useUrlState already supports arbitrary multi-field state.

    pathfinderUrlParams alone carries 5 independent keys with their own encode/decode.

    Consequence: adding scenario and a literal schedule sequence is pure reuse — encode the actual thread-pick sequence, not an index into a results list that could reorder later.

  4. Adding a whole new domain is mechanically cheap.

    Confirmed against how BST/Heap were added: one entry in the navRoutes array plus one view file is the entire surface — no other central registry exists.

    Consequence: none of this item's effort is registration. All of it is the search layer and the new multi-thread view.

  5. Interleaving counts blow up fast past a handful of threads.

    A racy counter (2 threads × 3 instructions) has 20 interleavings. Dining philosophers (5 threads) has more than is sane to enumerate — see the slider above.

    Consequence: v1 is deliberately scoped to two exhaustively-checkable scenarios, so it never has to defend an incomplete result for its flagship bugs.
